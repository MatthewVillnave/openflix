OpenFlix Technical Specification

Version: 0.1 Draft
Status: Architecture / implementation handoff
Project type: Open-source self-hosted media aggregation and federation platform

⸻

1. Project Summary

OpenFlix is a standalone open-source media platform that sits in front of existing media servers, beginning with Jellyfin.

OpenFlix does not replace Jellyfin’s media engine.

Instead:

Jellyfin handles

* Media files
* Library scanning
* Media metadata
* Playback information
* Direct streaming
* Transcoding
* Subtitle/audio tracks
* Hardware acceleration
* Existing local media administration

OpenFlix handles

* A unified user-facing application
* Jellyfin server discovery/connection
* Cross-server catalog aggregation
* Search across multiple libraries
* User identity and sessions
* Playback brokering
* Remote access abstraction
* Federation between OpenFlix nodes
* Node discovery
* Shared-library permissions
* Trust and catalog validation
* Eventually creator/public/community catalogs

The simplest conceptual model is:

                OPENFLIX CLIENT
                     |
                     v
                OPENFLIX NODE
                /     |      \
               /      |       \
          Jellyfin  Jellyfin   Remote
          Server A  Server B   OpenFlix Node

A user interacts only with OpenFlix.

OpenFlix determines where the requested media lives and obtains the stream from the appropriate Jellyfin server.

⸻

2. Core Design Principle

OpenFlix must separate:

1. Media storage
2. Media serving/transcoding
3. Catalog/indexing
4. Identity
5. Federation
6. Client presentation

No OpenFlix deployment should require all six functions to exist on the same physical machine.

A Raspberry Pi, OptiPlex, VPS, NAS, home server or cloud VM should all be capable of running an OpenFlix node.

The actual media may remain somewhere completely different.

Example:

VPS
└── OpenFlix Node
Home Server
└── Jellyfin
    └── /media
        ├── Movies
        ├── TV
        └── Music
Browser / Phone / TV
└── OpenFlix

The VPS does not need a copy of the media.

It communicates with Jellyfin and brokers playback.

⸻

3. Major Components

OpenFlix should initially consist of four logical components.

3.1 OpenFlix Server

The primary backend application.

Responsibilities:

* Authentication
* User accounts
* Connected-server management
* Catalog database
* Search
* Jellyfin API communication
* Playback authorization
* Stream brokering
* Federation
* Node identity
* Peer management
* Permissions
* Health checks
* Audit logs

Suggested implementation:

Language: TypeScript
Runtime: current Node.js LTS
HTTP framework: Fastify
Database layer: Drizzle ORM or equivalent
Primary DB for v0.1: SQLite
Future supported DB: PostgreSQL
API style: REST + WebSocket/SSE events

SQLite is desirable for the initial version because OpenFlix should remain easy to self-host.

The target installation experience should eventually be:

docker compose up -d

5. Jellyfin Connector

OpenFlix requires an abstraction called a Media Connector.

The first connector implementation is:

JellyfinConnector

This abstraction is important because OpenFlix should not permanently become synonymous with Jellyfin.

Future connectors could potentially support:

PlexConnector
EmbyConnector
FilesystemConnector
CreatorFeedConnector
ArchiveConnector

Core interface:

interface MediaConnector {
    connect(): Promise<void>;
    testConnection(): Promise<ConnectionResult>;
    getLibraries(): Promise<Library[]>;
    scanCatalog(): Promise<MediaItem[]>;
    getItem(id: string): Promise<MediaItem>;
    search(query: string): Promise<MediaItem[]>;
    getPlaybackInfo(
        itemId: string,
        clientProfile: ClientProfile
    ): Promise<PlaybackInfo>;
    reportPlaybackStart(session: PlaybackSession): Promise<void>;
    reportPlaybackProgress(session: PlaybackSession): Promise<void>;
    reportPlaybackStop(session: PlaybackSession): Promise<void>;
}

OpenFlix code outside the connector layer should not depend directly on Jellyfin-specific API response objects.

6. Connecting Jellyfin

The administrator should open:

OpenFlix
→ Settings
→ Media Servers
→ Add Server
→ Jellyfin

Configuration:

Name:
Living Room Server
URL:
http://192.168.1.100:8096
Authentication:
<Jellyfin-supported connector credential>
Connection mode:
LAN / HTTPS / Private Network

OpenFlix performs:

1. Resolve server.
2. Query Jellyfin system information.
3. Authenticate.
4. Store resulting connector credential securely.
5. Enumerate accessible libraries.
6. Ask administrator which libraries to import.
7. Begin catalog synchronization.

OpenFlix should never retain the Jellyfin user’s plaintext password after authentication.

7. Connector Security

Stored connector secrets must be encrypted at rest.

Example:

OPENFLIX_MASTER_KEY

is supplied using an environment variable or secret store.

Database value:

encrypted_connector_token

never:

plaintext_password

Connector secrets must never be:

* included in logs
* transmitted to browsers
* exposed in diagnostics
* included in federation metadata
* embedded into permanent playback URLs

8. OpenFlix Catalog

OpenFlix maintains its own metadata index, not its own copy of the media.

Example:

OpenFlix Database
Movie
├── OpenFlix ID: of_movie_8f731
├── Title: Interstellar
├── Year: 2014
├── TMDB ID: ...
├── IMDB ID: ...
└── Sources
    ├── Jellyfin Server A
    ├── Jellyfin Server B
    └── Remote OpenFlix Node C

Multiple physical copies of the same movie should appear as one catalog item with multiple sources.

9. Media Identity

OpenFlix requires a normalized media identity layer.

Preferred matching order:

1. External provider ID
2. Media type
3. Release year
4. Season/episode number
5. Normalized title
6. Runtime
7. Optional media fingerprint/hash

Example canonical identity:

type = movie
tmdb = 157336

For television:

type = episode
tmdb-series = ...
season = 2
episode = 4

File names must never be treated as sufficient proof that two media objects are identical.

11. Library Synchronization

When Jellyfin is first connected:

Jellyfin
   |
   | scan
   v
OpenFlix Connector
   |
   | normalize
   v
OpenFlix Catalog

Initial v0.1 synchronization should use polling as the authoritative mechanism.

Example:

Initial full scan
then
Incremental synchronization every 5 minutes

Synchronization handles:

Added media
Changed metadata
Deleted media
Library changes
Artwork changes
Server availability

Later OpenFlix can use Jellyfin real-time events where appropriate as an optimization.

Polling remains the reconciliation mechanism.

13. Playback Architecture

This is one of the most important parts of OpenFlix.

The client requests:

POST /api/v1/playback/start

Example:

{
  "catalogItemId": "movie_abc",
  "clientCapabilities": {
    "videoCodecs": ["h264", "hevc"],
    "audioCodecs": ["aac", "opus"],
    "maxWidth": 1920,
    "maxHeight": 1080
  }
}

OpenFlix:

1. Resolves available sources.
2. Checks user permission.
3. Checks source availability.
4. Selects preferred source.
5. Requests playback information from Jellyfin.
6. Creates OpenFlix playback session.
7. Returns temporary OpenFlix playback URL.

15. Direct Mode

For trusted local environments:

OpenFlix
   |
   | signed temporary request
   v
Client
   |
   v
Jellyfin

Useful when both devices are on the same LAN.

This prevents OpenFlix itself from becoming a bandwidth bottleneck.

16. Relay Mode

Future feature.

Useful for a Jellyfin server behind:

CGNAT
NAT
Firewall
No inbound ports

Concept:

Jellyfin/OpenFlix Node
        |
        | outbound encrypted connection
        v
OpenFlix Relay
        |
        v
Viewer

The relay routes traffic.

It does not need to permanently store the media.

Relay mode is NOT required for v0.1.

17. Transcoding

OpenFlix should not implement its own FFmpeg transcoding system in the MVP.

That is Jellyfin’s job.

Example:

Browser cannot play source format.
OpenFlix
→ Jellyfin playback request
→ Jellyfin selects transcode
→ Jellyfin/FFmpeg generates compatible stream
→ OpenFlix proxies generated stream
→ Browser

OpenFlix is the orchestration layer.

Jellyfin remains the media engine.

22. Federation

This is the major long-term OpenFlix feature.

An OpenFlix server becomes an:

OpenFlix Node

Nodes can communicate with other OpenFlix nodes.

Example:

Matt Node
   |
   +------ Alice Node
   |
   +------ Bob Node
   |
   +------ Community Node

No single OpenFlix server needs to contain the entire network.

23. Node Identity

On first startup every OpenFlix node generates:

Ed25519 public/private key pair

Node ID:

SHA-256(public key)

Example:

ofnode_94e92f...

Private key remains on the node.

Public key identifies the node to peers.

24. Node Descriptor

Every node exposes:

GET /.well-known/openflix

Example:

{
  "protocol": "openflix",
  "protocolVersion": "1",
  "nodeId": "ofnode_94e92f",
  "name": "Matt's OpenFlix",
  "api": "https://node.example.com/api/v1",
  "federation": true,
  "publicKey": "...",
  "capabilities": [
    "catalog",
    "search",
    "playback"
  ]
}

Descriptor should be digitally signed.

Do NOT begin v0.1 with a DHT.

Build federation progressively.

v0.1

→ Federation

Later

26. Federation Handshake

Node A contacts Node B:

A → /.well-known/openflix
B → NodeDescriptor
A verifies:
protocol
version
signature

Node A sends signed handshake:

{
  "nodeId": "...",
  "timestamp": 123456789,
  "nonce": "...",
  "signature": "..."
}

Requests must include replay protection.

29. Federated Search

User searches:

Bluey

Home node searches:

Local catalog
+

The user’s client should not need to independently query 500 servers.

Their home OpenFlix node performs aggregation.

Result:

Bluey
├── Local source
├── Node ABC
└── Node XYZ

Displayed as one title.

30. Federated Playback

Example:

Viewer
   |
   v
Home OpenFlix Node
   |
   | signed playback request
   v
Remote OpenFlix Node
   |
   v
Remote Jellyfin

Remote node decides whether the requesting node/user is authorized.

Remote Jellyfin credential never leaves the remote node.

Possible final path:

Viewer
→ Remote OpenFlix Node
→ Remote Jellyfin

using a temporary playback capability created by the home/remote-node handshake.

This avoids double-proxying through the home node.

⸻

31. Temporary Playback Tokens

Federated playback URLs must be temporary.

Example claims:

{
  "session": "ps_93d",
  "media": "item_123",
  "user": "user_abc",
  "sourceNode": "node_xyz",
  "expires": 123456789,
  "permissions": ["stream"]
}

Token should:

expire quickly
be signed
be limited to one media item
not permit arbitrary API access
not expose Jellyfin credentials

⸻

32. OpenFlix Is Not a File Upload Site

This is a deliberate architectural decision.

There should initially be no endpoint resembling:

POST /upload/movie

OpenFlix discovers media through connectors.

Example:

Jellyfin contains media
↓
OpenFlix indexes it
↓
Administrator chooses whether it is shareable

This keeps OpenFlix fundamentally different from a generic video-upload platform.

⸻

33. Catalog Trust

A node claiming:

Cars (2006)

does not automatically mean OpenFlix should trust that claim.

Possible trust states:

UNVERIFIED
NODE_VERIFIED
HASH_VERIFIED
MANIFEST_VERIFIED
CREATOR_VERIFIED

This architecture allows stronger verification later without changing the basic protocol.

⸻

34. Media Fingerprinting

Optional future feature.

For public/shared content, OpenFlix may calculate:

SHA-256

for exact-file verification.

For multiple legitimate encodes of the same media, future perceptual/audio/video fingerprints may be used.

Exact hashes identify files.

Metadata identifiers identify works.

These concepts must remain separate.

36. Node Trust

Users should be able to:

trust node
block node
remove node
report node
restrict node

Example:

Alice Node

Last Seen: 22 seconds ago

37. No Single Global Administrator

OpenFlix federation should not require one master administrator.

Each node controls:

its users
its connected Jellyfin servers
its shared catalog
its peer relationships
its access rules
its blocks
its trust decisions

The protocol coordinates nodes.

It does not centrally own them.

49. Failure Handling

If Source A fails during startup:

OpenFlix retries Source B.

If stream dies mid-playback:

MVP:

show playback failure
offer retry

Future:

resume from equivalent Source B

Cross-source seamless failover is not required for v0.1.

50. Security Requirements

Mandatory:

* HTTPS for internet-facing nodes
* strong password hashing
* CSRF protections where applicable
* secure cookies
* strict CORS
* Content Security Policy
* rate limiting
* connector-secret encryption
* federation signatures
* replay protection
* nonce validation
* request size limits
* safe URL validation
* SSRF protection
* parameterized database queries
* no secrets in logs
* short-lived playback capabilities

OpenFlix should assume peer nodes may be malicious.

Never trust federation input merely because it came from another OpenFlix installation.

68. Design Rule: OpenFlix Must Work Without Federation

This is important.

Even if federation disappeared tomorrow, OpenFlix should remain useful as:

A beautiful open-source unified frontend for one or more self-hosted media servers.

That ensures the project has immediate value.

⸻

69. Design Rule: Federation Must Work Without OpenFlix Central Infrastructure

Likewise:

Two OpenFlix nodes controlled by two independent people must eventually be capable of federating directly.

Node A
↔
Node B

No mandatory:

openflix.com
central login service
central database
central streaming server

A hosted OpenFlix service may exist for convenience.

It must not be required by the protocol.

⸻

70. Design Rule: Storage Belongs to the Node Operator

OpenFlix does not require users to upload their media into an OpenFlix-owned cloud.

Example:

Matt owns 8 TB storage.
Alice owns 20 TB storage.
Bob owns 4 TB storage.

They remain owners/operators of their storage.

OpenFlix provides the interoperability layer.

⸻

71. Design Rule: Compute Belongs to the Source

If a source Jellyfin server needs to transcode:

source Jellyfin performs transcoding

The requesting node should not normally do it.

This distributes compute naturally with the media.

⸻

72. Design Rule: Metadata Can Travel, Secrets Cannot

Federation can exchange:

title
description
poster
year
runtime
provider IDs
quality
availability
catalog IDs

Federation cannot exchange:

Jellyfin administrator token
filesystem paths
private keys
local network credentials
database passwords
unrelated user information

⸻

73. Long-Term Vision

OpenFlix eventually becomes an open protocol for decentralized personal and community media infrastructure.

Conceptually:

                   OPENFLIX
              Open Client Layer
                      |
              Identity / Catalog
                      |
              Federation Protocol
             /        |        \
            /         |         \
       Home Node   VPS Node   Community Node
          |           |            |
       Jellyfin    Jellyfin      Jellyfin
          |           |            |
       Storage     Storage       Storage

The important innovation is not merely a different Jellyfin skin.

It is:

A unified media experience where the catalog, storage, compute and users can live on independent hardware while interoperating through an open protocol.

A person’s media server becomes one node in a larger optional network rather than an isolated island.

75. Instructions to Implementation Agent

Treat this document as the architectural specification for the OpenFlix project.

Begin with Milestone 1 only.

Before implementing:

1. Inspect the current Jellyfin API/OpenAPI specification.
2. Inspect the current official Jellyfin TypeScript SDK.
3. Do not assume legacy Jellyfin endpoints remain valid.
4. Establish the monorepo and test environment.
5. Create architecture documentation.
6. Implement interfaces before Jellyfin-specific business logic.
7. Keep federation packages present structurally but do not implement federation during Milestone 1.
8. Keep media-server-specific objects behind the MediaConnector abstraction.
9. Make no changes to the connected Jellyfin installation.
10. Never expose Jellyfin credentials to the OpenFlix web client.

After Milestone 1, produce:

STATUS
TEST RESULTS
FILES CREATED
ARCHITECTURE DECISIONS
SECURITY NOTES
KNOWN LIMITATIONS
NEXT MILESTONE

Do not proceed automatically into later milestones until the current milestone is independently testable and its acceptance criteria pass.

The immediate goal is not to build a global streaming network.

The immediate goal is to create a clean architecture capable of becoming one.
